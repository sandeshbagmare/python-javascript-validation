01 / THE RECOMMENDATION

Best overall balance: Acorn, hosted by Python.

For this application, choose pinned Acorn 8.19.0 inside mini-racer==0.14.1. The container needs Python and its native wheel, not Node.js. Execute the trusted parser and pass generated JavaScript as data; never evaluate the submitted program.

The priority is to avoid flagging valid code as broken, while tolerating occasional missed edge cases. On the expanded corpus Acorn-V8 wrongly rejected 0/302 valid samples and missed 1/305 invalid samples. Its parser has substantial adoption, and the V8 route handled our depth-300 valid probe. This is a practical tradeoff, not a mathematical proof or an unconditional winner for every workload.

This default assumes a persistent worker and an acceptable native-engine footprint: the V8 worker peaked at approximately 103 MiB RSS in this run. If that memory budget is too high, the QuickJS host's approximately 33 MiB observed peak makes it the better deployment tradeoff, with its tested default-stack limitation handled as inconclusive.

Why not simply choose Tree-sitter? Low false alarms alone do not favor it: Tree-sitter rejected 3/302 valid samples, but missed 259/305 invalid samples. It remains an excellent fast structural/advisory screen. Once useful error detection is included, Acorn catches substantially more without a measured false-alarm penalty in this corpus.
Why not the pure-Python fork? esprima-fork==5.0.0 recorded 0 false rejects and 0 missed invalid cases. Credit that result. However, its snapshot shows 0 repository stars, 129 monthly distribution downloads and a roughly four-year gap preceding the latest release. It also reaches resource limits on deeply nested valid inputs. It is the strongest tested pure-Python alternative, but its independent scrutiny and maintenance continuity are less established. The recommendation deliberately trades a disclosed Acorn edge-case miss for stronger ecosystem evidence.

Choose the host deliberately

Acorn in QuickJS-NG has the same parser logic, a smaller deployment footprint and a more recently released wrapper. It is a credible alternative when size matters. The V8 route is the default here for broader listed platform support, greater wrapper adoption and better depth tolerance in our tests—not because two hosts are two independent validators. mini-racer's latest release was February 2026; its age is a real maintenance consideration, not hidden by V8's reputation.

Acceptance policy: a parser-reported syntax error is a candidate for repair only under the correct Script/Module and language-version contract. Timeouts, unsupported configurations, resource exhaustion and crashes are inconclusive, not broken JavaScript. If avoiding false rejection dominates everything, make uncertain outcomes advisory. Syntax acceptance still does not guarantee correct rendering.

02 / CHOOSE YOUR LEVEL

Choose the promise before you choose the parser.

“Valid” can mean structurally plausible, syntactically legal, compatible with a particular browser, or actually working. Those are different contracts. Here is how to choose without buying complexity you do not need—or trusting a check that does not make the promise you think it makes.

01 / LIGHT CHECK

Catch obvious malformed structure.

Recommended: Tree-sitter 0.26.1 with JavaScript grammar 0.25.0.

Inspect root_node.has_error, then walk both ERROR and MISSING nodes. Return NO_STRUCTURAL_ERROR_FOUND or NEEDS_REVIEW. This catches incomplete expressions and unclosed source while retaining useful error locations.

Use it for: editor feedback, cheap first-pass diagnostics, or workflows where missed invalid code is acceptable. Keep it advisory if false rejection is the highest concern.

Accept the cost: let x; let x;, break;, const x; and JSX can produce clean trees. The benchmark recorded 259 missed invalid cases and three false alarms. That is not a production rate, but it establishes that this is not a complete JavaScript validator.

02 / GOOD DEFAULT

Check grammar and early errors.

Recommended: Acorn 8.19.0 through mini-racer 0.14.1. The Python wheel supplies the engine; your container does not need Node.

Use the actual Script/Module goal, an explicit edition, and ordinary strict-parser options. Pass generated source as an argument to the trusted parser. Reuse one context per worker, and keep source size, wall-clock time and memory bounded.

Use it for: a delivery gate for generated source where low false alarms and useful invalid detection both matter. It accepted all 302 valid samples and missed one of 305 invalid samples.

Accept the cost: a native engine, roughly 103 MiB measured worker peak RSS, startup overhead, separate parser/host updates, and a documented static-block early-error miss. An accepted result means syntax accepted, not “the UI works.”

03 / PURE PYTHON

A stricter check without an engine wheel.

Recommended candidate: esprima-fork 5.0.0, qualified against your own source distribution. Set ecmaVersion=2025, tolerant=False, and jsx=False.

Use it when: Python portability or native-wheel restrictions outweigh the maintenance uncertainty. It agreed with all 607 labels in this study, including the Acorn counterexample.

Accept the cost: limited independent adoption and a long historical release gap. Valid nesting hit the resource limit at depths 100 and 300. Return INCONCLUSIVE, not invalid syntax, for these diagnostics. Install it alone: all three Esprima distributions use the esprima import namespace.

04 / STRONGEST ASSURANCE

Test the actual environment as well.

No parser offers a rendering guarantee. Start with the strict syntax gate, then use an isolated browser test stage with the same origin, CSP, assets, dependencies and supported browsers as production. Exercise the expected interactions and collect console, network and DOM failures.

This stage needs infrastructure beyond the Python-only parser container: an independently provisioned browser worker or CI service. It was not implemented or benchmarked in this study.

For higher syntax assurance, a second parser may be useful as a disagreement detector. Do not blindly require both parsers to pass: that can increase false rejection when either parser has a limitation. Send disagreements and infrastructure failures to review.

The strongest honest promise: “passed these source checks and these browser scenarios under these pinned conditions.” Arbitrary JavaScript behavior cannot be universally guaranteed by a finite test suite. Security review and isolation are separate requirements.

A concrete decision sequence

  1. Are native Python wheels allowed? If yes, Acorn’s embedded hosts are eligible. If no, qualify the modern fork. Do not confuse “no Node” with “no JavaScript engine of any kind.”
  2. Is this a warning or a release gate? Tree-sitter is reasonable for warnings. A gate deserves a strict, context-aware parser with explicit failure categories.
  3. Is ~103 MiB worker memory acceptable? If not, consider Acorn + quickjs-ng, whose worker peaked around 33 MiB. Its default stack reached a limit at depth 300; stack tuning was not part of the experiment.
  4. Must it work, not just parse? Add a separate browser-scenario stage. Missing functions, broken DOM selectors and failed imports remain outside the syntax verdict.
  5. Can a failure be ambiguous? Yes. A timeout is not invalid syntax, and an unsupported dialect is not necessarily broken source. Preserve those distinctions in your API.

Why each candidate received its position

The ranking is an ordered engineering judgment: low false rejection first, useful invalid detection next, then deployment, operational limits and maintenance. It is not a score produced by adding stars to accuracy.

Researched but not in the seven-run benchmark

  • pyswc / SWC bindings: wrapper age, platform coverage and limited parse-goal controls prevented a like-for-like deployment recommendation. This does not rank SWC core as a poor parser.
  • Babel parser: valuable for JSX/TypeScript/proposals, but extra bundling/options and regex-pattern-validation qualification make it a different integration. Not measured here.
  • Meriyah: host-dependent regex validation and explicit lexical-check configuration require separate qualification. Not measured here.
  • QuickJS compile-only APIs: the C capability is not automatically exposed by every Python wrapper. Do not call a wrapper’s eval or module execution API and label that syntax-only validation.
  • new Function(source): changes the parse goal to a function body, incorrectly accepts a top-level return for a classic script, and does not parse modules correctly.
  • Regex/bracket counting: cannot resolve comments, literals, template substitutions, lexical rules, automatic semicolon insertion or scope. A quick heuristic is not a language parser.

Illustrative response schema, not a verbatim benchmark record. Preserve the parser’s actual diagnostic. Record script identity and location units so the UI can highlight the correct source. Do not claim the column is an HTML-document offset unless your extraction layer supplies a tested source mapping.

Suggested caller policy: valid proceeds; invalid requests a focused repair; inconclusive retries under a controlled policy or goes to review. Never endlessly regenerate code because the validator ran out of memory. Store original source and diagnostics to build a production regression set rather than relying only on this article’s corpus.

Three traces worth remembering

const x=; → grammar failure: a variable initializer needs an expression.

let x; let x; → Tree-sitter constructs a clean tree, but Acorn rejects a duplicate lexical binding.

Highlighting is not the same as validation

A recovery parser can return a useful tree even when the source is incomplete. A strict parser adds rules such as “this binding already exists” or “this statement is not allowed here.” These are different capabilities. Do not interpret the existence of an AST as proof that the browser accepts the program.

One important Acorn miss

class C { static { const f = () => arguments; } }

This is invalid: class static-block ContainsArguments checks descend through arrows. The corresponding ordinary function may use its own arguments. Both Acorn hosts accept this pinned-version counterexample; the fork rejects it. An independent reviewer confirmed the expected label against ES2025 ContainsArguments. No untested patch is quietly applied to inflate Acorn's score.

All source units, expected labels and observed outcomes—not just the examples—are linked below.

HTML relevance of Tree-sitter's three false rejections: they involve a hashbang terminated by U+2028, a carriage-return-containing comment that permits automatic semicolon insertion, and a sloppy arrow parameter named yield. Normal HTML preprocessing converts CR to LF before JavaScript parsing, so the raw-CR fixture is a parser-conformance edge case rather than evidence that your HTML pipeline will produce that failure. Hashbang placement is also sensitive to leading text/newlines. These caveats do not change the raw-JavaScript labels, but they limit the inference about real generated HTML.

06 / HOW WE TESTED

Reproducible backtesting, not a completeness claim.

  • Seven pinned configurations run in separate fresh Linux/Python 3.13 jobs, on the same frozen source corpus.
  • Official Test262 provenance preserves source path, commit, original-source hashes, chosen parse goal, strictness transformation and exclusion rules. See the full manifest rather than assuming every upstream test is eligible.
  • Only parse-phase negatives are labeled invalid. Runtime failures and missing host functions do not make source syntax-invalid. Resolution negatives and out-of-contract proposals are excluded by the corpus builder.
  • Each parser runs in a spawned worker. A five-second external deadline bounds each call; a failed worker is retired. Inconclusive outcomes are reported separately and do not become successful invalid detection.
  • Script and Module are not interchangeable. The fork and Acorn explicitly use ES2025; other packages use their shipped grammar and are evaluated against the same labels, with that mismatch disclosed.
  • All Esprima distributions are installed in separate environments because they share the esprima import name.
  • The initial independent-context proposals were challenged by corpus, scope, specification, maintenance and final-article reviewers. They use the same model family; this is not cross-model proof or a popularity vote.

The 500-file standards subset is deterministic, not random production traffic. Feature families and fixtures are correlated. The study does not establish a production false-positive probability, exhaust all ECMAScript syntax, or constitute a full Test262 run. It is also not a “backtest” of historical LLM output: no representative user production dataset was supplied. For deployment, add your actual model's accepted and rejected outputs as a regression set.

The pinned snapshot is May 31, 2025, with a conservative feature policy—not a complete final-edition inventory. The subset spans 195 directories but favors richly subdivided class/generator/destructuring families; only 24 of its 500 samples use Module. Feature tags are metadata, not proof that a syntax form occurs in the outer program (a RegExp-constructor test may contain no regex literal). The original modern-syntax cases complement this limitation; neither subset alone establishes exhaustive feature coverage. An independent reviewer checked all 500 labels, transformations and source/body hashes against the pinned archive.

Case IDs and paths retain upstream provenance; Test262 source notices and its license are preserved. No expected label was selected by asking the favored parser.

Where each approach fits

  • Tree-sitter: fast, mature parsing ecosystem; helpful recovery and source ranges. It includes JSX and omits many early-error rules. A clean tree is not a browser-validity guarantee.
  • Original Esprima: stale modern-syntax coverage; false rejections make it a poor fit here.
  • Modern Esprima fork: strongest tested pure-Python strict option; smaller adoption and depth constraints.
  • esprima2: portable but misses scope/context errors found by the stronger validators.
  • Oxc Python wrapper: fast native parser; the inspected v0.1.1 binding omits Oxc's semantic syntax-checking pass. Its results do not evaluate the full Oxc toolchain.
  • Acorn: modern grammar, source-goal and early-error checking; needs a vendored trusted bundle plus a Python engine wheel. Embedded engine execution is only for the parser.

Decision rule

  1. Correct context and honest failure classification first.
  2. Minimize false rejections on the valid sample set.
  3. Among comparably low-false-alarm choices, prefer useful invalid detection.
  4. Then weigh deployability, operational limits and maintenance/adoption.

There is no arbitrary weighted “stars score.” Acorn's overall recommendation is a disclosed engineering judgment: strong validation plus established parser adoption, at the cost of a native engine dependency, startup overhead, wrapper maintenance and a known missed edge case. If pure Python is mandatory, use the fork instead; if only advisory structural feedback is needed, Tree-sitter remains reasonable.

09 / SHIP IT IN PYTHON

The recommended Python snippet.

python -m pip install mini-racer==0.14.1

Vendor Acorn 8.19.0's prebuilt bundle as acorn.js alongside this module and retain its MIT license. The snippet verifies the exact bundle hash. No npm or Node installation is needed in the application container. The tested API uses Python ≥3.10 with a compatible native wheel.

"""Node-free strict syntax check: only trusted Acorn code executes."""
import hashlib
from pathlib import Path

from py_mini_racer import MiniRacer

ACORN_SHA256 = "b95392d79457d0357555c5ed3e56302d074b92dff119bcf3b44179500b10e9df"
WRAPPER = """
function checkJavaScript(source, mode) {
  try {
    acorn.parse(source, {ecmaVersion: 2025, sourceType: mode});
    return {status: "valid"};
  } catch (error) {
    if (error instanceof SyntaxError &&
        !error.message.startsWith("Not enough stack space")) {
      return {status: "invalid", message: error.message,
              line: error.loc.line, utf16Column: error.loc.column};
    }
    return {status: "inconclusive", reason: "parser_resource_or_internal_error"};
  }
}
"""


class JavaScriptValidator:
    """Use one context per worker; close it when that worker is retired."""
    def __init__(self, acorn_path: str):
        bundle = Path(acorn_path).read_bytes()
        if hashlib.sha256(bundle).hexdigest() != ACORN_SHA256:
            raise ValueError("Unexpected Acorn bundle: expected pinned 8.19.0")
        self.context = MiniRacer()
        try:
            self.context.eval(bundle.decode("utf-8"))
            self.context.eval(WRAPPER)
        except Exception:
            self.context.close()
            raise

    def check(self, source: str, mode: str = "script") -> dict:
        if mode not in ("script", "module"):
            raise ValueError("Use the actual script or module parse goal")
        if len(source.encode("utf-8")) > 256_000:
            return {"status": "inconclusive", "reason": "input_size_limit"}
        try:
            # Pass source as an argument; never interpolate it into eval().
            return self.context.call("checkJavaScript", source, mode, timeout=2000)
        except Exception as exc:
            return {"status": "inconclusive", "reason": type(exc).__name__}

    def close(self):
        self.context.close()

validator = JavaScriptValidator("acorn.js")
try:
    result = validator.check(extracted_script, mode="module")  # actual HTML type
finally:
    validator.close()

Reuse one context per worker rather than initializing on every request. The 256,000-byte input cap and two-second embedded deadline are example policies, not language rules. The external worker deadline used in the benchmark is additional to this compact helper; use process-level memory limits and deadlines for a service. Infrastructure exceptions remain inconclusive. SyntaxError locations use one-based lines and zero-based UTF-16 columns. Do not append those directly to Python scalar or UTF-8 byte offsets.

The integration checks verify modern syntax, duplicate bindings, module/script await, size handling, deep input, JSX rejection and the documented edge-case miss. A sentinel check confirms submitted assignment code is parsed without being executed. Acorn can construct input-derived RegExp objects while building its AST; no matches or submitted statements are run. Parsing is still resource-consuming native work.

Keep the HTML boundary correct

Use your existing BeautifulSoup extraction deliberately: preserve raw script text, classify classic/module/data, and parse each source unit separately. External src is unchecked unless its source is supplied. JSON/JSON-LD requires a strict JSON parser; import maps and speculation rules need their own schema rules too.

A literal </script> can terminate HTML script content even inside a JavaScript string. Comment termination can leave a valid but unintentionally truncated program. HTML escaped/double-escaped states, noscript, templates, namespaces and handlers need correct context. Do not HTML-unescape script bodies. Event-handler attributes are different and can legally contain return.

Expanded boundary checks and exact observed outcomes: HTML/JSON regression results. There are 76 passing assertions and 4 context observations, measured separately on Windows/Python 3.14.8 with BeautifulSoup 4.15.0 and html5lib 1.1. Their scope and limitations are recorded; no full browser rendering test is claimed.
